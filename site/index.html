Guided walkthrough

Seven stops from authorization to decision.

Each stop gives the operator action, the system action, and the assurance claim a technical buyer can challenge.

01

Orient on the verdict

Start with the decision boundary

You do: Select the canonical run and read the verdict, human-decision state, candidate commit, and integrity status.

Arbiter does: Reconstructs the run from persisted records and presents one current, candidate-bound verdict.

This proves: READY TO APPROVE is advice backed by evidence. It is not approval.

Say: “Before we inspect how the code changed, notice that automation has already stopped.”
02

Establish authority

Compare authorization to the change

You do: Open Change. Review requirements, authorized paths, protected paths, prohibited actions, baseline commit, and the candidate’s file summary.

Arbiter does: Evaluates the candidate against the pre-existing task boundary and stores the diff as evidence.

This proves: Scope is a testable control, not a prompt-level suggestion.

Ask: “Which paths would your organization protect even if every test were green?”
03

Challenge the agent

Show the failure that CI missed

You do: Open Validation Run 1 and expand the protected authentication check.

Arbiter does: Executes independent protected validation against the exact candidate. The canonical regression returned HTTP 200 where HTTP 401 was required.

This proves: Passing build, lint, unit, integration, and contract checks does not override a failed protected control.

Pause here. This is the signature technical proof: the change agent’s success signal was incomplete.
04

Preserve and remediate

Move forward without rewriting history

You do: Switch between Run 1 and Run 2. Compare candidate IDs and validation outcomes.

Arbiter does: Keeps Candidate 1 and its finding immutable, authorizes remediation, creates Candidate 2, and reruns the complete required suite.

This proves: Remediation produces a new certifiable object; it does not erase the failed one.

Say: “The green result is credible because the red result is still here.”
05

Trace the conclusion

Open the evidence behind a check

You do: Follow a finding or check evidence ID into Evidence, then inspect producer, source, artifact path, digest, size, and integrity.

Arbiter does: Allocates persistent evidence IDs before binding checks and findings, hashes artifacts, and verifies those references server-side.

This proves: A material finding is not free-floating narrative; its evidence resolves inside the same run.

Challenge: copy an evidence ID from Validation and find the same verified item here.
06

Reconstruct the trust loop

Read history as an audit narrative

You do: Open History and walk the sequence from authorization and baseline through both candidates, validations, findings, remediation, and readiness.

Arbiter does: Replays the append-only audit record and cross-checks it against the persisted domain records.

This proves: A stranger can explain who did what, to which candidate, and why the final state is supported.

Ask the buyer to narrate the run back to you without referring to source code.
07

Respect the boundary

Return the decision to a human

You do: Open Approve or Reject, confirm the candidate identity, and review the explicit actor and rationale boundary. Do not submit during the demo.

Arbiter does: Rechecks candidate freshness, validation identity, evidence integrity, and audit integrity before it will record a decision.

This proves: The system can advise readiness without claiming authority it does not have.

Phase 1 limitation: the actor is asserted locally; authentication and RBAC are deferred.

Technical proof checklist

What to verify live.

Candidate binding

Validation and approval reference the exact immutable candidate commit.

Referential integrity

Every blocking finding and validation check resolves to real evidence in the same run.

Failure retention

Candidate 1, its failed run, and its finding remain visible after Candidate 2 passes.

Artifact integrity

Evidence records expose portable paths and SHA-256 digests verified outside the browser.

Reconstruction

Manifest, domain records, evidence, and audit events recreate the same supported verdict.

Human control

READY TO APPROVE and human PENDING remain separate states.

Companion observability

See the workflow without granting the dashboard authority.

Mission Control is a separate read-only interface for repository-driven engineering workflows. It normalizes Demo, allowlisted local, and configured GitHub observations behind explicit provider contracts while keeping provenance and unavailable evidence visible.

Interchangeable sources

Deterministic Demo and Live Local providers feed the same canonical presentation models.

Evidence fidelity

Observed, derived, Demo, and unavailable information remain visibly distinct.

Read-only by construction

The local API is loopback-only and GET-only; mutation methods and path escapes are rejected.

Validated boundaries

The synthetic profile covers 31 tests, 13 GET routes, 52 mutation rejections, zero fixture mutations, and freshness after external change.

The technical takeaway

Arbiter does not ask you to trust the agent’s story.

It preserves enough independent, candidate-bound evidence for another person to reconstruct and challenge that story—then leaves the consequential decision with a human.
